# Static recompilation engineering audit (2026-10-18)

**Baseline:** main at 9f63ee39c656bfd3f1e906827d4ae6830d2fda3c. **Scope:** source inspection and test review, not a full runtime/game execution. Findings below are source-level defects or implementation gaps and need synthetic regression tests before being marked closed.

**Status on the audit branch (`audit/2026-10-18-integral-audit`, re-verified 2026-10-18):** PPC-001…PPC-013 are fixed with regression tests — the differential harness compiles 185 synthetic programs and every defect mutation re-introduced in the sources is detected (10/10). RUN-001…RUN-006 stay open (tracked by the [implementation plan](../architecture/implementation-plan.md)) — except RUN-001 (partially: the exact-name coreinit registry landed 2026-10-19 with strict unknown-call semantics — four identity calls plus nine flat-memory/cache primitives — and the five proc_ui lifecycle models, 18 input models and four deterministic clock/system-info models landed 2026-10-20; filesystem, threading, the scheduler and the rest remain open), RUN-002, addressed by the 2026-10-19 load-image follow-up below, and RUN-003, addressed by the 2026-10-19 checked-memory follow-ups including per-section write protection; RUN-007 is partially addressed (CI runs the node suites, C syntax checks, the compiled ISA/loader/memory conformance and the HLE contract test); RUN-008 no longer reproduces (the architecture README now records ADR-0002). Evidence under *Fix verification results*.

**Follow-up (2026-10-19, RUN-002 — RPX load image):** `node tools/ppcx/ppcx.js image --rpx …` validates and serializes every allocated section of the module into a self-describing `PPCXIMG1` blob: **31 segments, 43,155,811 bytes** (41,756,342 data + 1,399,469 BSS), **278,749 `R_PPC_ADDR32` data relocations applied**, **889,935 executable-section sites left to the recompiler** and **6 TLS (`DTPMOD32`/`DTPREL32`) sites deferred explicitly** with their addresses (three `.rodata` TLS variables). The runtime (`src/runtime/src/ppcx_image.c`) validates structure, segment order, guest-arena bounds and a Fletcher-32 payload checksum **before** it writes anything, and maps the image only when `PPCX_IMAGE` points at it (the default demo behaviour is unchanged). Built from the copy whose SHA-256 matches the recorded v208 digest; the blob builds in ~1.5 s and the compiled demo maps it in ~0.13 s. Synthetic fixtures and ten corrupted-blob classes are compiled and checked in `tests/loader`. No game boot, HLE or rendering is implied.

**Follow-up (2026-10-19, RUN-003 — checked guest memory):** the unchecked raw-pointer path is replaced by a region model (`src/runtime/src/ppcx_mem.c`). `ppcx_mem_reset` — called by `ppcx_run` before the entry point — activates checking and maps the stack (1 MiB below `0x10000000`); the image loader registers every segment of a `PPCX_IMAGE` blob, so a loaded image is exactly the set of addresses translated code may touch. Every guest accessor (`ppcx_rd*`/`ppcx_wr*`, the byte-reversed and `dcbz` variants, and the string/multiple-register helpers that use them) requires the access to fall **entirely inside one region**; otherwise it prints one deterministic diagnostic line plus the register context and exits with code 9 (64-bit range math, so a 32-bit address wrap cannot slip through). The loader gains failure code **-10** (a segment overlaps a live region or the region table is full), raised before the mapping loop. The blob now carries the ELF writable bit (`SHF_WRITE`) per segment, so regions have permissions: the stack and the writable segments accept writes, while a write to a read-only segment (`.text`, `.syscall`, the import tables or the allocated metadata on v208) prints a second deterministic diagnostic — naming the region tag, start and size — and exits with code 9. On v208, 5 of the 31 segments are writable (`.rodata`, `.data`, `.module_id`, `.bss`, `.thrbss`; 6,140,245 bytes) and 26 are read-only (37,015,566 bytes). Verified with a new compiled harness in `tests/mem` (region registration and sorted listing with permissions, duplicate/overlap/invalid/conflicting return codes, first/last-byte boundaries, unaligned and host-order accesses, `dcbz` block bounds, thirteen illegal accesses — nine outside every region and four writes to a read-only one — each exiting 9 in its own process with the exact diagnostic and empty stdout, the fault hook for both fault kinds, run-to-run determinism), the extended `tests/loader` (checked probes of a relocated synthetic image, per-segment permission probes, idempotent re-registration after a second load, and a second process writing to the loaded read-only `.text` with exit 9) and a re-run of the demo with and without the real v208 image (exit 0, transcript unchanged). No game boot or HLE behaviour is implied.

**Follow-up (2026-10-19, RUN-001 — typed HLE memory/cache primitives):** the exact-name registry (`src/runtime/src/ppcx_hle.c`) grows from four identity calls to 13 coreinit functions. The nine new models are the highest-count memory/cache imports in the v208 census: `OSBlockMove` (6,834 REL24 sites + 2 address-taken; memmove-like, overlap supported, returns `dst`), `coreinit.memcpy` (408 + 2), `OSMemoryBarrier` (330 + 2, host fence), `OSBlockSet` (295 + 2, `uint8_t` value, returns `dst`), `DCZeroRange` (119; zeroes the 0x20-byte blocks covering the range through `ppcx_dcbz`), `DCFlushRange` (77; range check + fence), `DCFlushRangeNoSync` (29), `DCInvalidateRange` (9) and `coreinit.memset` (84). Every memory service validates the whole range against the checked region map before touching memory, so a read-only destination, an unmapped destination/source or a read-only `DCZeroRange` block stops with the existing deterministic diagnostic and exit code 9, with no partial effects; zero-length ranges are no-ops. `OSBlockMove`'s overlap guarantee is implemented explicitly because the local TCC's `memmove` was measured to copy forward and corrupt an overlapping destination. The contract test (`tests/hle/test_hle.c`) now covers the 13 models, exact-name matching and register preservation on a raw arena; the compiled `tests/mem` harness links the same `ppcx_hle.c` with the real region map and adds 25 positive HLE lines plus four HLE fault processes (read-only destination, unmapped destination, unmapped source, read-only `DCZeroRange` block). The v208 demo still runs the same translated entry and reports `proc_ui.ProcUIInit` as unimplemented, so nothing here claims game boot or HLE compatibility.

**Follow-up (2026-10-20, RUN-001 — proc_ui lifecycle models):** the registry gains the five imported `proc_ui` functions (10 call sites in v208), closing the next block of RUN-001. `ProcUIInit` is modeled as void with its documented non-NULL save callback (NULL is rejected and counted); `ProcUIProcessMessages` returns `IN_FOREGROUND` (0) while initialized and `EXITING` (3) before init or after shutdown, records `block`, and has no scheduling effect; `ProcUIDrawDoneRelease` is a counted no-op; `ProcUIRegisterCallback` records `(type, fn, param, priority)` in a bounded 16-entry table (NULL callbacks rejected, overflow counted) and never invokes them; `ProcUIShutdown` ends the lifecycle. The six real registration sites use phases 5, 1, 0, 0, 1 and one caller-supplied value, measured at `0x2E25A58`, `0x2E25A70`, `0x2E25A88`, `0x3424F38`, `0x34ED708` and `0x34ED720`; the other sites are `ProcUIInit` `0x031FA4D4`, `ProcUIProcessMessages` `0x031FAB88`, `ProcUIDrawDoneRelease` `0x031FAB78` and `ProcUIShutdown` `0x031FAB9C`. The native contract test now covers 18 models (13 coreinit + 5 proc_ui), including reset/re-init, register preservation of the void calls, the bounded callback table and the post-shutdown status. `tests/boot` gained a ninth scenario (seven compiled entries, 50 transcript lines, 72 probe lines) that runs all five models through the real REL24 substitution and proves the post-shutdown status by returning `r3 = 0x47` (`EXITING` 3 + 0x44); the unmodeled import used by the tolerant/strict scenarios is now `coreinit.OSSleepTicks`, which keeps exit 5 covered. Re-running the real v208 graph method `FUN_031FA4CC` (`translate --fn 0x031FA4CC --follow 2`, image 31 segments / 43,155,811 bytes) now prints `HLE modeled #1: proc_ui.ProcUIInit (import 359), r3=0x031FA4C8`, returns `r3 = 0x031FA4C8` (the untouched void-call argument) and exits 0 under `PPCX_HLE_STRICT=1`. This is lifecycle bookkeeping, not HOME-menu, save-callback or full ProcUI behavior, and nothing here claims game boot or graphics.

**Follow-up (2026-10-20, RUN-001 — minimum input services):** the registry gains the 18 non-audio input imports between `padscore`, `vpad` and `vpadbase`, covering 22 REL24 sites measured in v208. The modeled `padscore` calls are `KPADGetMplsWorkSize` (model-chosen 0x100-byte work size), `KPADInitEx`, `KPADSetMplsWorkarea`, `KPADReadEx`, `WPADProbe` (always `WPAD_ERROR_NO_CONTROLLER`, -1, writes extension type 0 when the output pointer is non-NULL), `WPADStartSyncDevice` (FALSE) and `WPADEnableURCC` (counted no-op). The modeled `vpad` calls are `VPADRead`, `VPADGetTPCalibratedPoint`, `VPADSetSamplingCallback`, `VPADControlMotor`, `VPADStopMotor`, `VPADEnableGyroAccRevise`, `VPADDisableGyroDirRevise`, `VPADSetGyroAccReviseParam`, `VPADSetGyroDirection` and `VPADSetGyroZeroDriftMode`; `vpadbase.VPADBASEGetHeadphoneStatus` returns 0 (no headphones). The policy is a deterministic headless placeholder, recorded in [ADR-0003](../architecture/decisions/0003-headless-input-policy.md): one neutral virtual GamePad is present on VPAD channel 0, and a read with `count >= 1` writes one zero-filled 0xAC-byte `VPADStatus` (no buttons, centered sticks, invalid touch) and returns one sample. No KPAD/WPAD controller is present, so `KPADReadEx` returns 0 samples with `KPAD_ERROR_NO_SAMPLES` (-1) after init (and -5 `KPAD_ERROR_UNINITIALIZED` before it; channels outside 0..3 return -2 `KPAD_ERROR_INVALID_CONTROLLER`) and leaves the guest buffer untouched. Touch calibration is an identity copy of the 8-byte `VPADTouchData` (aliasing-safe), sampling callbacks are recorded and never invoked, motor patterns are accepted and discarded, and the five gyro setters are counted no-ops. Sizes and signatures were checked against wut `padscore/kpad.h`, `padscore/wpad.h`, `vpad/input.h` and `vpadbase/base.h` (`KPADStatus` 0xF0, `VPADStatus` 0xAC, `VPADTouchData` 0x08). The native contract test in `tests/hle` at that point covered **36 models** (13 coreinit + 5 proc_ui + 18 input; the clock block below takes it to 40), including the KPAD pre-init/post-init distinction, invalid-channel errors, untouched KPAD buffers, the VPAD 0xAC-byte write and error word, touch aliasing, callback return values, motor argument validation, gyro no-ops, WPAD no-controller behavior, reset, exact-name rejection of the still-unmodeled `KPADRead`/`VPADInit`/`WPADControlMotor`, and register preservation. Two real v208 wrappers were measured with the 31-segment / 43,155,811-byte image under `PPCX_HLE_STRICT=1`: `0x030C7558` (`translate --fn 0x030C7558 --follow 1`, 13 instructions, only `padscore.WPADProbe`) prints `HLE modeled #1: padscore.WPADProbe (import 355), r3=0xFFFFFFFF` and returns `r3 = 0`; `0x030D730C` (`translate --fn 0x030D730C --follow 1`, 12 instructions, only `vpadbase.VPADBASEGetHeadphoneStatus`) prints `HLE modeled #1: vpadbase.VPADBASEGetHeadphoneStatus (import 438), r3=0x00000000` and returns `r3 = 0`; both exit 0. The Wii Remote audio/motor path remains unmodeled (8 REL24 sites: `WENCGetEncodeData` 1, `WPADCanSendStreamData` 1, `WPADControlMotor` 2, `WPADControlSpeaker` 3, `WPADSendStreamData` 1), host input is not implemented, and `tests/boot` remains nine scenarios; input semantics are gated natively and by the real v208 wrappers, not by a synthetic boot scenario. Nothing here claims game boot, HLE compatibility, full input behavior or rendering.

**Follow-up (2026-10-20, RUN-001 - deterministic clock/system-info models):** the registry gains the four clock/system-info imports measured in v208: `OSGetSystemTime` (481 REL24 sites plus 2 address-taken sites), `OSGetTime` (10), `OSGetSystemInfo` (17) and `OSTicksToCalendarTime` (2), reached from 374 functions; 10 functions combine `OSGetSystemInfo` with another clock call. `OSSleepTicks` (7 sites) stays unmodeled because it needs a scheduler. The policy is [ADR-0004](../architecture/decisions/0004-deterministic-virtual-clock.md): a fixed **2026-01-01 00:00:00 UTC** virtual epoch (9,497 days after 2000-01-01, 51,001,739,100,000,000 ticks), a 62,156,250 Hz timer (bus 248,625,000 / 4), and one **1,035,937-tick** (1/60 s) advance per successful `OSGetSystemTime`/`OSGetTime` read. `OSGetSystemTime` returns ticks since virtual boot, `OSGetTime` adds the epoch, and both use the 64-bit `r3:r4` ABI. `OSGetSystemInfo` returns a pointer to the 0x20-byte `OSSystemInfo` at the reserved HLE data page `0x00090000` (`busClockSpeed` at 0x00, `coreClockSpeed` at 0x04, `baseTime` at 0x08, zero reserved bytes through 0x1F). `OSTicksToCalendarTime` consumes `r3:r4` and a pointer in r5, writes the ten 0x28-byte `OSCalendarTime` fields in UTC with Sunday = 0 and January = 0, and clamps negative inputs to 2000-01-01 (wday 6); there is no host timezone, DST or wall clock. The native contract test now covers **40 models** (17 coreinit + 5 proc_ui + 18 input), including exact 64-bit halves, clock counters/state, guest and host system-info fields, epoch/1.5 s/negative calendar cases, an untouched trailing byte and reset; exact-name negatives reject `OSGetSystemTimeEx`, `OSGetSystemInfoEx`, `other.OSGetSystemTime` and `OSGetTick`. The compiled `tests/mem` HLE extension maps `0x00090000` and reads `hle-sysinfo-base=00B531CFBDFB8F00` through the real checked accessors, for **31 positive HLE lines plus four HLE fault cases**. Two real v208 paths run under `PPCX_HLE_STRICT=1` with the same 31-segment / 43,155,811-byte image: `0x030CB524` (`translate --fn 0x030CB524 --follow 1`, 11 instructions, only `OSGetSystemInfo`) prints `HLE modeled #1: coreinit.OSGetSystemInfo (import 78), r3=0x00090000`, returns `r3 = 0` and exits 0; its disassembly computes `busClockSpeed / 4 = 62,156,250` in r4 after zeroing r3, a 64-bit `r3:r4` result that the runtime trace does not print. `0x0308E41C` (`translate --fn 0x0308E41C --follow 1`, 16 instructions, only `OSGetSystemTime`) prints `HLE modeled #1: coreinit.OSGetSystemTime (import 79), r3=0x00000000` (high word; first low word `0x000FCEA1`), stores both words at `0x105495A0/A4`, zeroes `0x105495A8/AC`, returns `r3 = 0` and exits 0. These runs prove strict import resolution and a readable HLE page on the real image; they do not claim host time, timer interrupts, scheduling, game-compatible timing or game boot.

**Follow-up (2026-10-19, Phase 2B — synthetic headless boot fixture):** `tests/boot` authors a game-free RPX (seven functions, three imports — one called through a REL24 site, one address-taken through an ADDR16 trampoline, one unmodeled — three relocated `.rodata` pointers with one addend, two deferred TLS sites, `.data`/`.bss` and the allocated metadata trio) and runs it through the real production path: `analyze`, the same `translateModule` emission the CLI uses (verified byte-identical on the v208 demo), `buildImage`/`serializeImage`, then the real `ppcx_runtime.c` + `ppcx_mem.c` + `ppcx_hle.c` + `ppcx_image.c` compiled with the generated unit and a small driver. Seven scenarios boot headless and compare every stderr/stdout line with fixture-authored expectations: a boot with `PPCX_HLE_TRACE`/`PPCX_DISPATCH_TRACE` checkpoints (entry dispatch, `coreinit.memcpy` via `bl`, trampoline dispatch `0x50000000`, `coreinit.OSBlockMove`, `r3 = 0x11223344`, two HLE calls), an unmodeled `proc_ui.ProcUIInit` tolerated as a counted no-op, `PPCX_HLE_STRICT=1` (exit 5 + register dump), a pointer-only getter reached from `.rodata`, a cross-range tail `b` whose generated unit contains `PPCX_TAILCALL(c, f_000100F0)` and whose result `r3 = 2` proves the jump entered the mid-body start after the skipped `addi r3,0,0x40` (entering the split function from its top would leave `0x42`), an unmapped read at `0x01000000` (exit 9), and the same boot without `PPCX_IMAGE` (exit 9 at the first data read instead of zeroes); guest-memory probes assert the applied relocations, the untouched TLS bytes and the copied `.data`/`.bss` words, and the boot run must repeat byte-identically. The fixture found two real defects, both fixed and gated: (1) address-taken imports were absent from the generated `ppcx_import_name` table — only REL24 sites were recorded — so a call through the dispatcher trampoline reported `unknown-import` and silently no-opped; `translateFunction` now reports `importAddrs` and `translateModule` unions them into the name table and the report (`calls`/`addressTaken`); (2) the initial SP sat exactly at the top of the mapped stack, so the loader's ABI frame was outside the region and the first standard prologue faulted on its LR save; `ppcx_run` now starts at `PPCX_INITIAL_STACK - 16`, inside the stack and 16-byte aligned. Mutation evidence: reverting the frame produced 10 failing expectations and changing one authored data word produced 4, each with the exact transcript/probe diff. The translated v208 entry still runs unchanged (`r3 = 0x031FA4C8`, `proc_ui.ProcUIInit` unimplemented, strict exit 5); no game boot or HLE compatibility is implied. *(Extended 2026-10-20: the fixture now also authors an inline three-entry branch table, boots eight scenarios — adding a computed `bctr` switch — and reports 8/6 entries/39 transcript/60 probe lines; see the branch-table follow-up below.)*

**Follow-up (2026-10-19, independent decode cross-check):** the whole decompressed `.text` (9,248,515 words) was disassembled with rizin through REA (`asm.arch=ppc`, `asm.bits=32`, `asm.cpu=ps`, `io.va=false`, 36 chunks) and compared word by word with `tools/ppcx/lib/decode.js` through the new `tools/ppcx/xcheck.js` (unit-tested; documents the exact rizin recipe; exits non-zero on a real disagreement). Result: **5,843,694 words with identical canonical mnemonics (63.1852%)**, **3,404,768 differing only by a documented assembler alias (36.8142%** — `mr`/`or`, `li`/`addi`, `slwi`/`rlwinm`, `btlr`/`bclr`, `subc`/`subfc`, `trap`/`twu`/`tw`, and 25 more), **zero real disagreements**, zero missing lines, and the same 53 data/illegal words rejected by both sides. The check found one real defect: XO 311 is `lhzux` (zero-extending update load), but the table named it `lhaux` and translated 37 module words as sign-extending loads, while XO 375 (`lhaux`, 11 words) was not decoded at all; `tests/isa/oracle.js` carried the same mistake, which is why the differential harness had not caught it. Both sides are fixed (311 → `lhzux`, `u16` update; 375 → `lhaux`, `s16` update), with a decode unit test and five differential programs (`lhzx`/`lhzux`/`lhax`/`lhaux`, including the update order when rT = rA). Mutation evidence: the old decoder produces 3 mismatches, an oracle without XO 375 refuses the program (`oracle does not model: op31-xo375`) and an oracle with only the 311 sign-extension mistake produces 1 mismatch (`0xffff8080` vs `0x00008080`). Re-measured coverage: **9,248,462 supported words (99.9994%), 53 unknown/data, 96,865 fully supported functions** (was 96,857). No game boot, HLE or rendering is implied.

**Follow-up (2026-10-19, function-start cross-check):** the branch-derived starts and the pointer starts (`.rela.rodata` and `.rela.data`) were compared with the local Ghidra 12.1 headless census of the same module (97,363 functions: 96,946 in `.text` plus 417 named import stubs at `0xC000xxxx`). **96,052 of the 96,874 branch starts and 115 of the 104,499 pointer starts are census entries**, the 779 Ghidra-only in-`.text` entries are 362 tail-`b` targets (473 sites, no `bl` site) plus 417 others (tiny leaves after boundaries such as `addi r3,r3,8; blr`, `mr r11,r1; stwu …` large-frame prologues and a dense cluster of 8-byte non-prologue entries around `0x04004xxx`), and the 822 ours-only starts are 498 `bl` targets and 324 prologue-after-boundary entries that no census function even covers — sampled sites are real calls in the rizin dump and Ghidra has multi-kilobyte gaps there (e.g. nothing between `0x04232C18` and `0x042335F4`), so the census is a lower bound, not a completeness reference. **Follow-up (2026-10-20, inline branch tables and CTR dispatch):** the last recorded indirect-target class — computed `bctr` switches — was audited on the real module: 5,671 `bctr` sites were classified by their CTR source (5,126 load-dynamic-base vtable tails, 263 `addi`-dynamic, 177 inline `b`-tables, 68 zeroed runtime tables, 31 `addi`-constant targets, 3 offset tables, 2 indexed absolute tables, 1 call-clobbered). The 177 inline tables match the exact Metrowerks shape (static `addis`/`addic` base, scaled index, `add`, `mtctr`, `bctr`; every table base is `bctr + 4`) and hold **2,986 `b` entries** of 7–82 words; **2,979 of their case targets have no other static edge** (7 branch backwards into the switch body). They are now a separate `tableStarts` class (`ANALYSIS_VERSION` 9), promoted into the translation-range union and used to seed the cross-range fixpoint; the static callee walk cannot see them, so the synthetic boot fixture lists them as explicit roots. Re-measured on v208: **2,986 table starts**, **3,275 tail starts** (up from 518; strict superset, none lost), union **207,634 ranges**; the invariant re-check over 828,267 in-text `b`/`bc` pairs now reports 27,798 start hits and 800,469 intra-range pairs with **zero dispatch gaps** (the 2026-10-19 figures above — 518 / 201,891 / 20,476 / 807,791 — describe the pre-table v8 model). Census coverage is unchanged: 360 of the 362 tail-`b` entries remain covered. Extending `tests/boot` with a switch scenario exposed a real decoder/translator defect: canonical `blr`/`bctr` returned no `BO`/`BI`, so the translator gated the dispatch on `ppcx_bc(c,0,0)`; `BO = 0` decrements CTR, so the computed target shifted by one word (`0x1013C → 0x1013B`). The decoder now emits `bo: 20, bi: 0` for both canonical words, the translation is a bare `PPCX_DISPATCH`, and a regression assertion checks that no `ppcx_bc` gate is emitted. The boot fixture (eight scenarios, six entries, a `switch` case returning `r3 = 0x11` after dispatching to `0x1013C`) and the full battery are green; the v208 demo is unchanged (`r3 = 0x031FA4C8`, strict exit 5). No game boot, HLE or rendering is implied.

## Fix verification protocol

1. Add a failing synthetic test for every confirmed defect before touching translator/runtime.
2. Compare actual CPU GPR/FPR/CR/XER/LR/CTR plus guest memory to an independently reviewed PowerPC oracle, including signed extremes, zero, carry, bit-mask wrap, Rc and LK.
3. Compile emitted C with a real host compiler and run it; do not rely on generated-string assertions alone.
4. Run existing npm tests and host compile/sanitizers as supported; record observed pass/fail count, tool versions and commands.
5. Test safe failure on out-of-bounds memory, unknown relocations, unsupported imports and truncated RPX files.
6. Run actual game tests only locally with contributor-owned game files. Never upload generated C, disassembly, assets, dumps or keys.

Steps 1–4 were executed for the PPC items on the audit branch (below); steps 5–6 remain mandatory for loader/runtime work.

See [port survey](../research/2026-10-native-port-patterns.md) and [implementation plan](../architecture/implementation-plan.md).
